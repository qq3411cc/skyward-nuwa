# 结论

上游 `kirklin/skyward` v0.2.0 在 `nuwa` 上「不解密 data」不是坏了，是这套构建里没有起解密要用的服务：`devices/nuwa.toml` 里只有 `init.kernel.post_boot.sh`、两个触摸程序，qseecomd / keymint / gatekeeper 一条都没有。skyward 的解密实现编在 `/system/bin/recovery` 里，能力在，只是没被配置启用。

# 改动

`devices/nuwa.toml`：

1. `[firmware] partition = "modem"` —— 原厂 `init.recovery.qcom.rc` 只在 `on fs` 里 `mkdir /vendor/firmware_mnt` 并把 `/vendor/firmware_mnt/image` 绑到 `/vendor/firmware`，modem 本身没人挂；不挂，keymint 的 TA 就加载不了
2. `[partitions] mounted = ["persist"]` —— 不能回滚的密钥要用的文件在 persist（nezha 同款做法）
3. 六条 `[[service]]`，顺序即启动顺序：
   - `/vendor/bin/qseecomd`：`libraries=[/system/lib64,/vendor/lib64]`、`ready_property=vendor.sys.listeners.registered`、`user=root`、`groups=[root,drmrpc]`
   - `/vendor/bin/hw/android.hardware.security.keymint-service-qti`：`ready_service=IKeyMintDevice/default`、`registers=[IRemotelyProvisionedComponent/default, ISecureClock/default, ISharedSecret/default]`、`user=system`、`groups=[system,drmrpc]`
   - `/mnt/system_ext/bin/hwservicemanager`：`libraries=[/mnt/system/system/lib64/bootstrap, /mnt/system/system/lib64, /mnt/system_ext/lib64]`、`ready_property=hwservicemanager.ready`、`user=system`、`groups=[system,readproc]`
   - `/vendor/bin/hw/android.hardware.gatekeeper@1.0-service-qti`：`ready_hardware_service=android.hardware.gatekeeper@1.0::IGatekeeper/default`、`user=system`、`groups=[system]`
   - `/vendor/bin/hw/android.hardware.boot@1.2-service`：`ready_hardware_service=android.hardware.boot@1.2::IBootControl/default`、`user=root`
4. 没有 weaver 段：本机 secret 是 secdis + gatekeeper 绑定，`data.rs` 的 weaver 回退用不上

# 底座（原厂 recovery）的取法

`[stock]` 钉的是 `OS3.0.312.0.WMBCNXM`（公开可下的最新一版，7.15 GB 完整更新包），recovery 分区 SHA-256 `04431f150316d32fc5fd38ac8caf7e48ee271fa47cd23a28ad7e067e5fcde273`。

`tools/payload_get.py` 用 HTTP range 只取该分区占的 23.4 MB blob（50 个 op，REPLACE_BZ / REPLACE_XZ 混用），实测 SHA-256 与配置一致：

```
recovery: size=104857600 ops=50 types=[1, 8]
blobs 5262686984..5286094992 (23408008 bytes)
wrote dump/recovery_stock_os3.img 104857600 bytes
sha256=04431f150316d32fc5fd38ac8caf7e48ee271fa47cd23a28ad7e067e5fcde273
MATCH
```

原厂 recovery 结构：`ANDROID!`、kernel_size=0、ramdisk 27717188（lz4 legacy）、`AVBf` 尾（orig_size/vbmeta_offset=27721728、vbmeta_size=1472）。ramdisk 解包后 49 MB cpio，有 `system/bin/recovery`（2.8 MB）、`system/etc/recovery.fstab`、`prop.default`，没有 `twres` / `FFiles`（所以 `skyward-pack recovery` 的第三方 recovery 检查会通过）。

payload 格式的坑（都踩过）：

- payload.bin 头是**大端**：`CrAU`、version(>Q)、manifest_size(>Q)、metadata_signature_size(>I)，之后才是 manifest、元数据签名、blob
- 分区尺寸在 `PartitionUpdate.new_partition_info.size`（field 7 的嵌套 field 1），不在 field 7 本身
- `Extent` 是 `start_block=1`、`num_blocks=2`，写反了会得到一份全是 0 的镜像

# 构建

宿主是本机 Debian（aarch64），NDK 只提供 x86_64 预编译工具，所以用系统 clang 19 + NDK 的 sysroot 与 compiler-rt、链接器用 lld：

```
clang --target=aarch64-linux-android30 --sysroot=<ndk>/sysroot -rtlib=compiler-rt \
      -L<ndk>/lib/clang/21/lib/linux -fuse-ld=lld
```

clang 找 builtins 是按自己的 resource dir 找的，所以要把它指到 NDK 那份：

```
mkdir -p /usr/lib/llvm-19/lib/clang/19/lib/aarch64-unknown-linux-android30
ln -sf <ndk>/lib/clang/21/lib/linux/libclang_rt.builtins-aarch64-android.a \
       /usr/lib/llvm-19/lib/clang/19/lib/aarch64-unknown-linux-android30/libclang_rt.builtins.a
```

# 风险

- 只动 recovery 分区；出问题刷回原镜像（TWRP md5 `11e488f849bc323cbd43b8e2a4460a0e`）即可
- 镜像由 `skyward-pack` 打自己的 AVB 头尾（无签名，`algorithm=NONE`），与原厂布局一致；缺了这段 bootloader 不跳转，直接进 fastboot

# 真机第二轮：三处读同一个文件，只改一处不算改

v5 刷进去仍报 `read /data/unencrypted/mode: No such file or directory`。日志显示每次点「打开」都在 30 毫秒内失败——说明 `/data` 早就挂上了，卡的是挂载之后那句读文件。`data.rs` 里读这个文件的地方有**三处**：

| 函数 | 作用 | v5 | v6 |
|---|---|---|---|
| `open_shared()` | 让进「不属于任何用户」的文件的密钥 | 已容忍 | 已容忍 |
| `open_users()` | 让进每个用户「登录前可读」的文件的密钥 | **没改（就是它报的错）** | 已容忍 |
| `open_user_files()` | 用户登录后让进他自己的文件 | 没改 | 已容忍 |

三处都按「文件不存在 = 这台机器没加密」处理：`String::new()` 或空密钥名，随后 `users()` 返回空表，没有要解锁的用户。

# 真机第三轮：/sdcard 是空的

解密通了（日志 `data=open`），但 `/sdcard` 读写不到东西——截图存进了 `/sdcard/DCIM/Screenshots/`，重启就没了。

原因：`/sdcard` 是把 `/data/media/0` bind 上去的，而 `show_owner_storage()` 只在 `open_user_files()` 里、且 `user == OWNER` 时才调用。这台机器没有加密、`user_keys` 为空，那个循环一次都没进，绑定从未发生，`/sdcard` 一直是 ramdisk 里的空目录。

v7 在 `open_without_credential()` 末尾补一句：`closed.is_empty()` 时也调用 `show_owner_storage()`。未加密的机器、以及加密但已全部解锁的机器都会把 `/data/media/0` 绑到 `/sdcard`。
